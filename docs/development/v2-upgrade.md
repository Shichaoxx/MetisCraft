## 升级目标

v2 的首要交付是可复用的任务后训练流程：以一致的候选数据契约完成训练、任务评测、验证集选优、导出、重载及应用调用。先完成单选，再扩展多选和更多模型；架构收益、训练效果与运行成本分别验证。

首个交付应让使用者能够用同一个工具包训练排序和单选模型，而不必另写研究 runner。当前 Qwen3 Base + ScoreHead 和 yes/no 适配器继续作为可运行参照；统一 scorer 接口不要求所有模型采用同一 tokenizer、输入布局或读出。

v2 是工具包升级计划名称，不代表软件包已发布 `2.0.0`，也不代表底层模型架构已经改变。第一阶段完成前，README 继续如实描述 v1 的实现范围。

## 关键接口决策

| 边界 | 第一阶段约定 | 兼容要求 |
|---|---|---|
| 数据 | 保留 `query/context/candidates` 和稳定候选 ID；单选监督为完整二值标签且恰有一项为正 | 排序继续允许缺失判断，完整 qrels 保留候选外正例；不将缺失标签补零 |
| TaskSpec | 显式描述任务名、标签规则、概率语义、评测器、可选指标及指标方向 | 先覆盖已有三个任务名；Boolean/OrdinalScore 作为后续显式扩展，不一次替换全部 schema |
| Scorer | 输入样本，输出与候选 ID 对齐的有限 logits；可微张量入口用于训练，浮点入口用于推理 | 不把 Torch/Transformers 引入核心包的导入路径；保留现有两类适配器 |
| Evaluator | 排序用完整 qrels，单选用完整标签；CLI 与训练回调复用同一实现 | 不把 loss eligibility 子集冒充完整 dev，不输出只包含成功样本的 aggregate |
| Selection | 指标与方向显式记录；排序默认 nDCG@10/max，单选首版 NLL/min | 同分保持最早 step；随机初始化的 ScoreHead 仅作为诊断，不参与训练后 best 的竞争 |
| 概率 | 单选为有效候选内 softmax，多选为独立 sigmoid；排序默认只报告 raw scores | 概率输出采用显式 opt-in，旧 Predictor 默认字段与决策保持兼容；归一化不表示已经校准 |
| Calibration | 第一版为温度缩放；记录任务、拟合数据、候选协议、基座与 adapter 身份 | 参数纳入 sealed export 的哈希清单；拒绝将其他任务或模型的温度静默应用到当前产物 |
| Artifact | 新增语义元数据时明确记录版本与必需项，校验后再加载 | 不就地重写旧 manifest；读取器对新格式的支持先于写入器切换；缺失校准不冒充已校准 |

独立候选评分要求已有候选的 raw score 不随无关候选增删而改变。单选 softmax 的分母会改变，因此概率变化不违反 raw score 的独立性。联合候选交互是另一种 scorer 能力，后续须显式声明并单独对照。

通用 TaskSpec 复用现有 `Registry`，采用显式注册，不引入自动扫描与隐式插件导入。监督目标可按任务调用，但暂不建设任意训练算法或 attention backend 插件平台。

## 第一阶段：单选生产闭环

按以下顺序完成一个可运行增量，再进入校准与新模型。表中新增模块和命令是计划接口，不是当前可调用能力。

| 顺序 | 修改位置 | 具体工作 | 必须通过的验证 |
|---|---|---|---|
| 1 | `tasks/`、`metrics.py`、`schema.py` | 引入 TaskSpec 与统一评测入口；单选提供 accuracy、macro-F1、NLL、multiclass Brier | 极端 logits 数值稳定；候选 ID 对齐；缺失、重复、非有限分数及不完整单选标签拒绝；与手算例一致 |
| 2 | `config.py`、`training.py` | 移除只允许 ranking 的选优限制；将 `_selection_data`、`_complete_validation_metrics` 和 best 比较逻辑按任务分派 | 排序原语义回归；NLL 越低越好；同分最早；test 不参与训练/选优；train/dev/test 身份隔离 |
| 3 | `cli.py` | `metis evaluate --artifact` 按 manifest 与 artifact 的任务一致性分派；单选不要求 qrels | CLI 与训练回调同分；任务不匹配拒绝；失败写明原因且不生成成功报告；子集与完整评测有明确标记 |
| 4 | `api.py`、`tasks/decisions.py`、产物元数据 | opt-in 返回带候选 ID 的概率及语义；维护 raw scores 与旧决策接口 | 新旧产物重载；概率和为 1；换序一致；未知任务/语义拒绝；ranking 不自动被改成分类 |
| 5 | `tests/`、`examples/`、使用文档 | 用本地 tiny 模型完成 single_choice 的 full/LoRA 训练、完整 dev 选优、导出、重载与 CLI/Predictor 调用 | 所有步骤共享生产入口；实际参数更新；best/final 分离；恢复时选优历史与指标方向一致；无需 GPU 或下载 |

涉及 ranking 的既有集成测试应继续通过，包括完整 qrels 分母、零正例召回 query、产物篡改拒绝、恢复契约和候选换序。只增加与新行为或回归风险有关的测试，不按文件数量扩张测试。

默认单选选优采用 NLL，评价同时报告 accuracy 与 macro-F1。Macro-F1 的类集合必须预先声明；固定标签任务使用整个标签表，不能只计算预测中出现的类别。对每条样本候选集合不同的任务，accuracy/NLL/Brier 可聚合，macro-F1 仅在标签含义可跨样本对齐时计算。

NLL 从 logits 的稳定 log-softmax 计算，避免先得到下溢为零的概率再取对数；multiclass Brier 使用各类别平方误差之和，再按样本平均。多选指标与缺失判断另行定义，不能直接复用单选公式。

## 第二阶段：概率校准与决策质量

1. 固定已经选定的权重，使用独立 calibration split 拟合温度；dev 仅用于训练选优和方案筛选。数据不足时需另定交叉拟合协议，不在 test 上拟合。
2. 拟议新增 `metis calibrate` 命令，从已封存产物创建新的派生产物，保留来源哈希，不改写父产物。新产物同时保存未校准 logits 与温度语义，加载后可复现概率。
3. 报告校准前后 NLL/Brier、可靠性分桶和 risk–coverage；分桶和同置信度决策的 tie 规则固定。拒答阈值仅使用 dev/calibration 数据确定。
4. 单选的拒答基于最大选项概率或明确策略；它不同于 v1 的 raw `min_score`。旧参数不静默改义，新策略显式配置并随产物记录。

温度缩放通常不改变单选 argmax，不能将 NLL 改善描述为 accuracy 改善。校准不能修复模型没有利用证据的问题；出现全肯定或单类塌缩时先诊断训练。

## 第三阶段：第二个真实任务与轻量模型对照

建议首个新增生产 cookbook 采用 [Banking77 意图分类](../research/jev-task-survey.md)：标签含义固定、完整候选集明确，适合验证 single_choice 与生产接口复用。这里评估的是意图分类，不把离线准确率称为实际工具执行成功率。BoolQ 保留为独立训练诊断，不重复使用已看过的留出结果选择新方案。

数据和预算在真实计算前冻结，建议协议如下：

- 官方 train 内按类别划分 train/dev/calibration，目标比例 80/10/10、固定种子 42；去重或同源分组先于划分，逐类记录实际数量、缺类与跨 split 冲突。若无法兼顾隔离与覆盖，先修订协议。
- 官方 test 保持最终保留。77 个候选及其文本来自固定版本的标签表，不为省计算向每条样本注入正确标签或缩减为“含正确项”的小集合。
- 先用合成 tiny 数据验证链路，再以固定小规模 train/dev pilot 检查学习曲线、截断、各类召回与成本；pilot 不运行官方 test。正式训练上限、token 预算和资源计划在 pilot 后记录到独立 recipe。
- 基线至少包括 train 多数类、TF-IDF + 线性分类器、一个 encoder 分类方案、现有 Qwen3 Base + ScoreHead。先比较固定标签分类，不把 encoder 的标签 embedding 检索混作同一种模型。
- 固定数据与搜索预算，先单种子排错，再对选定方案运行三种子；默认不为所有架构展开全组合搜索。小规模或单种子结果只标记为 pilot。
- 模型、超参、温度和拒答策略全部冻结后才评测 test，并按样本或同源分组计算配对不确定性。离线指标与完整前向延迟分别报告。

第一轮真实任务的目标是确定可复用性与模型取舍，不预设 Metis 必须胜过 encoder。若简单模型在相近质量下成本更低，就将其作为任务推荐路线；是否接入新适配器由接口复用价值与测量结果决定。

## 第四阶段：按瓶颈升级模型与执行

先测 tokenization、padding、候选数、主干前向、冷/热启动及产物加载开销，再选择动态 batching、蒸馏或共享前缀实现。对齐输入协议、硬件、dtype、预热、计时同步和统计单位，报告 p50/p95、吞吐、峰值显存与质量。

候选交互、Boolean/OrdinalScore、更多 backbone、反馈 RL、分布式与稀疏 attention 保留为后续方向。共享前缀的推理缓存与训练反向图分别验证；dense tree 的正确性不能作为加速证据。没有任务或测量需求时不启动这些扩展。

## 验收与发布

第一阶段的完成条件是生产入口上的单选闭环和排序兼容回归通过；不要求用真实任务质量结果代替软件验收。第二、三阶段另行给出校准与真实任务报告。只有报告已经存在、结果可复现，才更新 README 中的能力与质量声明。

每个实现增量按影响范围完成离线测试和仓库检查；改变打包模块或格式后运行构建与分发检查；合并到完整 v2 候选版本时运行全套 CPU 回归。测试通过不自动更新历史配方或原始证据。

开发沿当前 `main` 顺序推进，用可独立回退的提交组织增量。新增运行独立输出；推送、软件发布、许可证与公开模型发布分别按实际任务处理，不由准备方案自动触发。

若单选仍不能超越无信息基线，暂停增加结构，先查标签映射、截断、输入泄漏、梯度和优化设置。若 decoder 在可接受质量下没有成本优势，保留其研究用途并优先考虑简单模型或 encoder；升级成功以工具包的实用性和证据判断。
